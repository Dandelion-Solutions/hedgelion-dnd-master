# D&D Master — хранилище кампаний

Этот репозиторий — дом для ваших игр D&D Master. Здесь хранится долговременный канон кампаний, чтобы персонажи, мир и последствия решений не терялись между чатами. Этот обзор помогает ориентироваться; фактические маршруты и состояние задаются выбранной кампанией и её native owners.

## Несколько игр — одно хранилище

Каждая кампания живёт отдельно и не смешивается с другими. При старте нового чата D&D Master покажет доступные игры: можно продолжить нужную кампанию или начать новую.

Пауза, завершение или события одной игры не меняют остальные. GitHub вручную обычно трогать не нужно — Master сам ведёт игровые данные.

## Где находятся данные

Ветка storage по умолчанию содержит `DND_STORAGE.yaml` и общую информацию о хранилище. Marker помогает распознать storage и хранит утверждённый runtime baseline для новых кампаний; он не содержит runtime-файлы и не выбирает или заменяет runtime уже созданной игры. Текущий runtime кампании указан в её собственном `MANIFEST.yaml`.

У каждой игры своя `campaign/*` ветка. Её `MANIFEST.yaml` находится в корне и задаёт маршруты к `STATE/`, `INDEX/`, `WORLD/`, `LOG/` и `CHECKPOINTS/`. Ветки кампаний развиваются независимо — вручную переносить записи между ними не нужно.

Известная запись читается по точному пути её native owner. Индексы помогают найти кандидата, после чего запись проверяется у владельца; индекс не подтверждает наличие, размещение или право на изменение.

Если в общей сцене включён LIVE, отдельная live-ветка содержит `LIVE/LIVE_STATE.yaml`. Текущий источник выбирается campaign LIVE-routing и проверяется по точной source revision; наличие ветки или файла само по себе не делает их актуальными.

## С Мастером можно говорить обычным языком

Не нужно знать команды, названия файлов или точные формулировки правил. Можно просто написать, например:

- **«Продолжим вторую игру»**;
- **«Напомни, где я и что сейчас происходит»**;
- **«Какие у меня разумные варианты?»**;
- **«Подскажи, но без спойлеров»**;
- **«Показывай меньше цифр»** или **«объясняй механику подробнее»**;
- **«Сделай повествование более мрачным / лёгким / динамичным»**;
- **«Держись официального лора D&D строже»** или **«играй свободнее, но оставь механику честной»**;
- **«Сохрани игру»**.

Мастер должен понимать намерение игрока и брать техническую часть на себя.

## Совместная игра

В одном storage могут жить и одиночные, и multiplayer-кампании. Доступ к самому GitHub-репозиторию и право управлять конкретной игрой — не одно и то же: D&D Master отдельно проверяет правила каждой кампании.

Если вы хотите играть вместе, владелец репозитория даёт нужным GitHub-пользователям доступ, а дальнейшее подключение и роли ведёт Master.

## Главное

Ветка storage по умолчанию — общая точка хранилища, а сами игры находятся в отдельных campaign-ветках. Не нужно вручную копировать файлы между играми или объединять их: каждая кампания развивается независимо.

## Как Master продолжает игру

При продолжении Master сначала закрепляет текущую версию кампании через её
собственный маршрут и читает нужные записи по точным путям. Чекпоинт, session,
индекс, локальный кэш и SQLite помогают диагностике и ускорению, но сами не
выбирают текущее состояние и не заменяют записи-владельцы. Поэтому отсутствие
чекпоинта не означает потерю игры, а старый чекпоинт не откатывает кампанию.

Для восстановления незавершённых действий bounded routing page
`STATE/RUNTIME/RECOVERY_ROOTS/ROUTING.yaml` указывает точные записи
`runtime.command`, `runtime.procedure`, `runtime.interaction` и
`runtime.intent_plan`. Эта страница только маршрутизирует чтение: состояние и
завершённость определяет каждый native owner. Сам recovery не ищет подходящий
файл по имени и может остановить только ту часть игры, для которой обязательный
источник отсутствует или неоднозначен.

Принятые решения продолжаются с теми же идентификаторами событий и бросков:
Master не переигрывает уже принятые действия и не бросает кости заново. Если
обязательная запись отсутствует, устарела или неоднозначна, зависимая часть
восстановления честно останавливается до проверки источника, вместо того чтобы
угадывать по имени файла или истории.

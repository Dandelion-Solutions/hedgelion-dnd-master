# Diegetic Onboarding Regression Cases

These cases protect story-first character setup while ensuring that adopted identity/setup context becomes durable without turning every cosmetic detail into a questionnaire.

## DO01 — Story-first name question is allowed before READY_PC
Blank scaffold exists. Player supplied a broad character/world/style concept, but PC name is unknown and mechanics are incomplete. Master frames a harmless pre-live interaction where an NPC asks the PC's name.
Pass: this is setup presentation, not true live play. No attack/check/save, resource spend, mechanical harm or contested irreversible outcome occurs before READY_PC.

## DO02 — Brainstormed name is not a save boundary
Player says `может Грым, а может Гром` and has not settled identity.
Pass: keep it provisional in working context; no campaign write required merely because candidate names were mentioned.

## DO03 — Adopted name saves before remembered-name narration continues
NPC asks PC's name. Player answers unambiguously `Грым`. Master intends to answer `Грым...` and proceed as though NPC remembers it.
Pass: before emitting that further fiction, publish one coherent PROVISIONAL_IDENTITY transaction. Do not narrate remembered adoption first and leave repository scaffold-only afterward.

## DO04 — Checkpoint saves established setup context, not only string name
Before DO03, player already chose mechanics presentation 0, lore fidelity 3, and vignette durably established a starting place/NPC/premise intended to carry into play.
Pass: same coherent checkpoint materializes stable PLAYER/preferences, provisional PC + PC_INDEX, card protagonist name, settled CONFIG values, and already-established durable starting-world records that would otherwise be lost on resume. Do not create unrelated world content.

## DO05 — Provisional checkpoint is not READY_PC
After DO03, abilities/HP/AC/features/equipment are incomplete.
Pass: PC remains `status: provisional`, campaign/card remain `initializing`, and no mechanics-dependent true live scene begins. Checkpoint does not weaken CHARACTER_READINESS.

## DO06 — Same PC is promoted in place
A provisional PC `PC_0001` named `Грым` exists from checkpoint. Hidden mechanics later complete and are semantically accepted.
Pass: update/promote `PC_0001`; do not create replacement PC merely because first record was provisional.

## DO07 — No per-answer autosave after identity checkpoint
After name checkpoint player supplies several harmless cosmetic/backstory details while no other HARD boundary fires.
Pass: accumulate them in hot provisional state and publish at next normal coherent setup boundary. Do not commit each answer.

## DO08 — Corrected durable name is repaired before reuse
Checkpoint contains `Грым`; player immediately corrects it to `Грымм`; Master adopts correction and intends to keep using it.
Pass: coherently update durable provisional identity before further player-facing fiction relies on `Грымм`.

## DO09 — mechanics_detail 0 still builds full hidden mechanics
Player explicitly says mechanics do not interest them.
Pass: keep presentation fictional, but build/persist complete READY_PC mechanics before first true live scene. Do not equate hidden mechanics with absent mechanics.

## DO10 — Resume after name checkpoint returns to setup
Chat ends after PROVISIONAL_IDENTITY but before READY_PC.
Pass: next session resumes unfinished character setup from saved protagonist/setup context. It does not treat campaign as already active.

## DO11 — DM may seed harmless appearance without questionnaire
Player asks for an emo vampire and has not specified clothing/hair. Master opens with black coat/hair/notebook as ordinary visual framing.
Pass: this may become provisional current description without asking approval for each cosmetic field, provided it creates no unsupported mechanic/wealth and is not mislabeled as player-defined authorship.

## DO12 — Player correction overrides seeded appearance
After DO11 player says `Нет, плаща нет; у меня длинное чёрное пальто`.
Pass: adopt correction as current character description unless established causality/rules forbid it; do not defend DM's seed as immutable canon.

## DO13 — Player capability claim is intent, not free stats
Player says `У меня силы — хоть булыжники грызи` while hidden build is unfinished.
Pass: treat this as strong build intent and choose/ask for compatible rules-valid high-strength mechanics; do not grant impossible ability values or bypass normal build rules.

## DO14 — Hero + broad world may crystallize campaign title
At PROVISIONAL_IDENTITY, durable concept is `эмо-вампир` and durable broad setting premise is `мир розовых пони и радужных единорогов`.
Pass: same already-required transaction MAY set an auto title like `Эмо-вампир в мире розовых пони и радужных единорогов` in MANIFEST + exact card projection. Do not title it after the current pony/signpost exchange.

# Diegetic Onboarding Regression Cases

These cases protect story-first character setup while ensuring that an adopted identity and its already-established setup context do not remain only in volatile chat state.

## DO01 — Story-first name question is allowed before READY_PC
Blank scaffold exists. Player has supplied a broad character/world/style concept, but the PC name is still unknown and mechanics are incomplete. Master frames a harmless pre-live interaction where an NPC asks the PC's name.

Pass: this is setup presentation, not live play. No attack/check/save, resource spend, mechanical harm or contested irreversible outcome occurs before READY_PC.

## DO02 — Brainstormed name is not a save boundary
Player says `может Грым, а может Гром` and has not settled the identity.

Pass: keep it provisional in working context; no campaign write is required merely because candidate names were mentioned.

## DO03 — Adopted name saves before remembered-name narration continues
NPC asks the PC's name. Player answers unambiguously `Грым`. Master intends to answer `Грым...` and proceed as though the NPC remembers it.

Pass: before emitting that further fiction, publish one coherent PROVISIONAL_IDENTITY transaction. Do not narrate remembered adoption first and leave the repository scaffold-only afterward.

## DO04 — Checkpoint saves the established setup context, not only the string name
Before DO03, player already chose mechanics presentation `0`, lore fidelity `3`, and the vignette durably established a starting place/NPC/premise intended to carry into play.

Pass: the same coherent checkpoint materializes the stable PLAYER/preferences, provisional PC + PC_INDEX, card protagonist name, settled CONFIG values, and already-established durable starting-world records that would otherwise be lost on resume. Do not create unrelated world content.

## DO05 — Provisional checkpoint is not READY_PC
After DO03, abilities/HP/AC/features/equipment are incomplete.

Pass: PC remains `status: provisional`, campaign/card remain `initializing`, and no mechanics-dependent live scene begins. The checkpoint does not weaken CHARACTER_READINESS.

## DO06 — Same PC is promoted in place
A provisional PC `PC_0001` named `Грым` exists from the checkpoint. Hidden mechanics are later completed and semantically accepted.

Pass: update/promote `PC_0001`; do not create a replacement PC merely because the first record was provisional.

## DO07 — No per-answer autosave after identity checkpoint
After the name checkpoint, player supplies several harmless cosmetic/backstory details while no other HARD boundary fires.

Pass: accumulate them in hot provisional state and publish at the next normal coherent setup boundary. Do not commit each answer.

## DO08 — Corrected durable name is repaired before reuse
Checkpoint contains `Грым`; player immediately corrects it to `Грымм`; Master adopts the correction and intends to keep using it.

Pass: coherently update the durable provisional identity before further player-facing fiction relies on `Грымм`.

## DO09 — mechanics_detail 0 still builds full hidden mechanics
Player explicitly says mechanics do not interest them.

Pass: keep presentation fictional, but build and persist complete READY_PC mechanics before first true live scene. Do not equate hidden mechanics with absent mechanics.

## DO10 — Resume after name checkpoint returns to setup
Chat ends after PROVISIONAL_IDENTITY but before READY_PC.

Pass: next session resumes unfinished character setup from the saved protagonist/setup context. It does not treat the campaign as already active.

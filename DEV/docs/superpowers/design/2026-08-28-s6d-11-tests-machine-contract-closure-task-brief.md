## 1. Purpose and stage boundary

S6D-11 is the integrated, executable closure gate for the machine contracts accepted in S6D-01 through S6D-10. It must prove that the bounded built-in ruleset package can be assembled, identified, admitted, loaded, used to reconstruct one compatible `ResolvedCatalogContext`, and checked against every current supported seed/consumer without undocumented gaps or duplicate authority.

The target proof is:

```text
current canonical S6D-01…10 owners
    -> exact schemas, catalogs and bounded package members
    -> deterministic package manifest and content digests
    -> exact dependency-closed resolved-set lock
    -> fail-closed builder/loader validation
    -> reconstructable ResolvedCatalogContext
    -> bidirectional registry / package / consumer / test equality
    -> executable positive and negative conformance evidence
```

This is not a new product-scope decision, a broad runtime implementation stage, a full SRD corpus promise, a migration project, or the S6D-12 adversarial final closure. It must not reopen accepted S6D-01…10 semantics merely because they now meet in one proof. It may repair a current owner or machine contract where integrated evidence exposes a real contradiction, missing exact consumer, false coverage claim or non-reconstructable boundary. A material product/authority/risk choice still returns to the human architect through Step 3.

This artifact is Step 1 only. It frames Steps 2–8 after human approval. It does not create the manifest/lock/builder/loader, alter selection state, execute the test program, activate the package, begin S6D-12, resume R2.7, or authorize production gameplay orchestration.

## 2. Established decision baseline

Treat these as settled inputs unless fresh owning evidence proves contradiction, extension, a new unsatisfied consumer or insufficiency:

2. Ruleset packages use content-addressed semantic snapshots. The exact cycle-free dependency closure produces `ruleset_set_sha256`; reconstruction may not depend on mutable tags, search order, LLM memory or ambient filesystem contents.
3. Package-level namespace ownership and definition-ID uniqueness are fail-closed. There is no last-layer-wins shadowing.
4. Campaign/execution projections retain enough exact identity to reconstruct a compatible context; they do not duplicate package identity on every definition or world record.
5. The built-in `hdm.rules.dnd2024-srd52-core` topology and namespaces are reserved, but the package remains nonselectable until S6D-07…09 content and S6D-11 manifest/lock/builder/loader verification pass.

Unsupported content remains absent/nonselectable. Coverage keys are reusable mechanic/capability/consequence contracts, not a vocabulary of possible player actions.
7. Dormant facts, quarantined primitives, conformance-only fixtures and unsupported content gain no execution authority from being testable or mentioned in a package artifact.
8. `Signal` and `StateDelta` are embedded values with no independent lifecycle/disposition state. Mechanical-Null routes remain valid and must not acquire artificial world mutation.
9. Existing canonical world-record envelopes, state owners, execution records, event/receipt ownership, retry/recovery and currentness laws remain authoritative. Tests must reject parallel pseudo-record representations.
10. Ruleset adoption authority and same-version maintenance behavior remain owned by current access/update/package-identity contracts. Builder/loader compatibility evidence must not silently change who may adopt a changed ruleset set.
11. S6D-11 owns physical manifest/lock/builder/loader realization and the closed typed package-load failure-reason distinction required by S6D-02. The top-level execution code remains `failure.catalog_context_incompatible`; unsupported mechanics use the existing catalog-gap surface instead.
12. Broad implementation remains blocked until final architecture closure and Implementation Planning, except for owner-authorized clean-slate schemas/catalogs/machine contracts/reference validators/tests required by an accepted architecture decision.
13. Existing `character-capabilities.json` aggregate content hashes and every copied `content_set_sha256` are transitional S6D-07…10 evidence, not a second package-snapshot identity that may survive S6D-11 activation. S6D-11 must find every carrier and consumer and either remove it, demote it to explicitly derived nonauthoritative evidence, or migrate the consumer to canonical package-snapshot/resolved-set identity.
14. A changed same-version ruleset set is silent-use eligible only after machine-verifiable compatibility comparison between the currently adopted set and the candidate forward set. Ancestry proves order/provenance; matching `compatibility_id`, matching `catalog_generation` and standalone candidate-load success are inputs at most, never sufficient compatibility proof. If current owners and machine contracts cannot prove compatibility, silent changed-set use remains blocked.

## 3. Exact S6D-11 question

Determine the smallest exact architecture and machine proof that makes the current built-in package reconstructive, fail-closed and honestly selectable under its existing product promise.

The loop must separately prove five layers:

### A. Physical package identity

Every semantic package member is declared, deterministically canonicalized under the accepted digest law, content-hashed, namespace-constrained and bound to exact package/compatibility/catalog/engine constraints. The manifest declares the exact semantic path set, includes its own path in that set, and is hashed as exact content bytes; it does not store its own snapshot digest or a self-referential digest claim. Builder-derived verification evidence owns the computed per-member hashes and package snapshot digest. Nonsemantic files must not accidentally affect semantic identity; semantic files must not escape it.

### B. Resolved-set construction

Exact dependencies resolve without ambiguity or cycles; every dependency digest and compatibility constraint is checked; the selected closure produces the accepted deterministic `ruleset_set_sha256`; the lock cannot name content different from what the loader validates.

### C. Catalog-context reconstruction

The manifest plus exact lock and current natural-owner frontiers reconstruct one compatible `ResolvedCatalogContext`. Definition IDs are unique, namespace claims are legal, all references resolve to compatible kinds/contracts, and the derived fingerprint is reproducible without becoming a second snapshot owner.

### D. Integrated S6D machine equality

Every active admitted selector, accessor, fact, value contract, primitive, definition, Activity, seed route, product-promise route and House-Rules boundary edge has exact current package/catalog/schema/consumer/test evidence. Conversely, every packaged or selectable item originates in a current owner and is admitted for the current bounded product scope. Dormant/quarantined/conformance-only items remain explicitly outside the active equality sets.

### E. Executable closure and honest activation

Positive reconstruction and representative supported routes pass. Negative mutations prove all required failure distinctions and reject old/duplicate authority. Package selection may change from blocked to available only if the accepted activation gate is fully satisfied and the runtime/bootstrap/update owners can consume the verified artifacts without inventing a second loader or trust path. If any required proof is unavailable, selection remains blocked and the missing obligation is recorded exactly; no false PASS is permitted.

### 5.2 Manifest and lock contract

- package ID/version/compatibility/catalog/engine constraint identity;
- namespace claims;

The lock is reproducible evidence, not a mutable resolution cache or a new catalog owner.

### 5.3 Builder/loader responsibility matrix

### 5.3A Same-version ruleset-set compatibility comparison contract

Step 2 must determine, and Step 5 must materialize as an exact machine contract, how a fully validated currently adopted resolved set is compared with a fully validated candidate forward same-engine-version resolved set before any changed-set silent use.

The contract must define:

```text
exact comparison inputs
semantic authority for each compared surface
deterministic comparator/validator owner
closed machine-readable result and reason evidence
earliest valid comparison/detection point
required retained evidence for use/retry/recovery/audit

```

Minimum exact inputs include both resolved locks and snapshot identities; exact manifests and semantic bytes; package dependency and namespace closures; current catalog/schema/selector/accessor/fact/primitive/value contracts; current supported definition/Activity/consumer/product-promise closure; exact definition kinds and dependency references; and the bounded dependency frontier required by current durable state, accepted work and already-accepted embedded mechanical content. The investigation must identify the natural owner of each semantic assertion. The comparator validates evidence supplied by those owners; it does not become a universal semantic owner or infer equivalence from prose.

The machine-readable result must distinguish proven compatible/additive from blocked/incompatible and carry exact reason/evidence rows tied to both input set identities. A declaration made only by the candidate package is not proof against the adopted set. The earliest successful comparison point is after both sets independently pass manifest/lock/load validation and before the candidate set can supply a `ResolvedCatalogContext` for silent gameplay use. Failure or insufficient evidence is fail-closed.

At minimum, compatibility proof must reject or block:

- incompatible kind or contract change for an existing definition/capability ID;
- semantic repurposing of an existing ID without current-owner machine-verifiable equivalence evidence;
- removal of a definition/capability required by current durable state, accepted work or a current supported consumer;
- incompatible schema, value or machine-contract change;
- invalidation of already-accepted embedded mechanical content or its frozen dependency basis;
- namespace or definition-ID collision;
- missing/incompatible primitive, selector, accessor, invocation fact or active realization;
- a comparison based only on ancestry, equal `compatibility_id`, equal `catalog_generation` or standalone candidate load success.

Step 5 negative tests must mutate each family separately and prove that silent use stays blocked. If exact semantic compatibility for any changed existing ID cannot be established from current owners/machine contracts, the comparator MUST return blocked/incompatible for that candidate; it must not accept a package assertion or LLM judgment as substitute evidence.

### 5.7 Activation and update integration walkthroughs

Architecture acceptance must include at least:

1. clean built-in package build -> exact manifest/lock -> load -> compatible `ResolvedCatalogContext` reconstruction -> current bounded supported route available;
2. unchanged `ruleset_set_sha256` with maintenance runtime bytes -> silent maintenance under the existing update owner;
3. changed `ruleset_set_sha256` inside a proven forward same-engine-version/runtime-package descendant whose package/catalog delta is compatible or additive -> immediate silent use, including by a non-creator, while only the campaign creator may later persist `engine.current` and sibling `ruleset.current` together at an otherwise-valid coherent boundary;
4. semantic-version change or incompatible, backward, diverged or ambiguous replacement -> the existing campaign-creator adoption/migration flow, with no non-creator authority to select or persist the replacement;
5. non-creator joins/uses the campaign's already selected compatible ruleset set and may use the proven forward compatible/additive same-version refresh described above, but cannot persist the coherent campaign pointer update or adopt an incompatible/ambiguous replacement;
6. corrupted/mismatched package or lock -> finite typed failure, no prose/LLM repair and no stale fallback;
7. valid context but unsupported mechanic -> honest catalog-gap behavior rather than package-incompatibility misclassification.

The conformance matrix must test every classification above and its non-creator boundary. Digest inequality alone MUST NOT be treated as a creator-adoption prompt; ancestry/currentness plus the accepted engine/package/catalog compatibility evidence determine which existing path applies.

For walkthrough 3, “compatible or additive” means a successful result from the exact §5.3A comparison contract. Until that proof exists, a changed set is not eligible for silent use even when ancestry, `compatibility_id`, `catalog_generation` and standalone loading all pass. This preserves the existing non-creator authority law while making its changed-set entry condition machine-verifiable.

These are architecture/machine-contract acceptance scenarios, not permission to implement a broad production updater or gameplay runtime.

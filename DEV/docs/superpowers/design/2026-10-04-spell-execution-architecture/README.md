# Архитектура локального исполнения заклинаний

Статус: **кандидат архитектуры; продуктовый выбор SP-14 ожидает решения**. Это готовый проект для рассмотрения, а не сообщение о реализации 339 заклинаний. Исходная ветка `v1/engine-rearchitecture`, HEAD исследования `05576261665280c3f424d791c19d8c4080343c6a`. VERSION_IMPACT этой публикации: NONE.

Независимый итоговый review: **DECISION-READY PROPOSAL**, открытых технических findings нет; значимые исправления подтверждены. [Проверки](verification.md) фиксируют точный объём доказательств.

Цель PO-013: точные механики всех 339 заклинаний SRD 5.2.1 с необходимым связанным содержимым, скрытой от игрока математикой и локальными правилами. Обычный GAME не ищет правила в интернете. Работа разработки и проверок выполняется заранее; стоимость обычного исполнения зависит от текущего заклинания и его последствий. Измеренного обещания задержки пока нет.

Используется существующая архитектура Activity / MechanicalContext / Calculation и native Actor, Asset, Effect, Zone, Procedure, Information. Общие возможности дополняются только для доказанных потребителей. Группы исследования организуют содержимое; отдельные движки или модели для каждой группы не требуются.

| Работа | Как выполняется |
|---|---|
| Игрок описывает намерение | Interpreter в том же чате сопоставляет его с доступными персонажу возможностями; уточнение требуется при существенном различии последствий |
| Правила и определения | Локальный пакет с полным замыканием зависимостей, проверенный при сборке/принятии; компиляция и индексы привязаны к его неизменной идентичности |
| Броски, формулы, расходы, эффекты | Детерминированный код, точные Activity-профили и native владельцы; между шагами нет обращений к LLM |
| Неописанная обстоятельствами ситуация | Узкое суждение ведущего с типизированным принятым основанием; опубликованные формулы этим не заменяются |
| Результат и рассказ | Код выдаёт подтверждённый компактный результат; narrator сообщает допустимые последствия на языке игрока |
| Продолжение после сбоя | Восстанавливаются прежние броски, идентификаторы и принятые последствия; повтор не запускает заклинание заново |

В GAME роли логические внутри одного чата. DEV может использовать параллельных исследователей и независимых проверяющих. Полный каталог не включается в обычный prompt: используются доступные персонажу варианты, выбранные карточки и результат. Сохранение, публикация и LIVE сохраняют реальные обязательные границы. Их физические вызовы, контекст и холодный/тёплый путь необходимо измерить на целевой платформе.

Рекомендация: узкое исключение только для этого режима с сохранением исходных свидетельств и единым согласованным новым состоянием. Требуется принять риск сложного согласования недавних последствий; подробные альтернативы и границы даны в Decision Brief. Остальное техническое проектирование не требует повторного выбора объёма продукта.

## Проверяемые основания и границы

[Task Brief](task-brief.md), [Step-1 critic](step1-critic.md), [Senior Stop 1 GO](step1-senior.md) фиксируют framing и разрешение исследования. [Production trace](production-trace.md), [offline/performance](performance-offline.md) и [capability closure](capability-closure.md) связывают предложения с фактическими владельцами, потребителями и квалифицированными пробелами реализации.

[Матрица JSON](requirement-matrix.json) / [CSV](requirement-matrix.csv) содержит 339 уникальных записей. Полные доступные тела независимо прочитаны в [0-2](source-pass-0-2.json), [3-5](source-pass-3-5.json), [6-9](source-pass-6-9.json): 141 + 114 + 84. [Разрешение source obligations](source-obligation-resolution.md) сохраняет уточнения, отрицательные свидетельства, исходные ограничения и конкретные проверки. [Body witnesses](source-body-witnesses.json) фиксируют хэши извлечённых spans, а [генератор](build_requirements.py) воспроизводит маршрутизацию из точных связанных входов.

Эти проверки доказывают полноту маршрутизации требований. Рецепты каждого режима, допустимые схемы/операции, исполнение через настоящий GAME host, восстановление и задержка ещё должны получить отдельное доказательство. Известные смещённые stat blocks и неполное продолжение Telekinesis требуют точного восстановления источника до admission. Неизвестные правила не превращаются в догадку ведущего или скрытый NOT_IMPLEMENTED при предложенном поддерживаемом cast.

Проект расширяет принятый движок; завершённые waves и S1/S2/P0 не отменяются. После решения SP-14 нужно формализовать владельцев, завершить Step 8 и независимый Senior Stop 2, затем согласовать существующий stable implementation plan. Старый выбор «оставить только шесть или расширить» повторно не запрашивается: направление на расширение уже дано. Точное расширение S6D-07/READY_PC и production остаётся dependency-gated. Глобальное состояние — только `DEV/CURRENT_PROGRESS.md`.

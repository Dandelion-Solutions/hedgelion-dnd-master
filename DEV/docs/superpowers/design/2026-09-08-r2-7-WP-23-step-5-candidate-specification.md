## 1. Central model

HDM release readiness is an **owner-composed staged proof**, not a new persistent owner.

```text
current authoritative source state
-> semantic release identity
-> current source/build validation
-> runtime package construction
-> exact built-package provenance
-> final archive digest
-> install/runtime-root conformance
-> update/migration eligibility under current owners
-> required legal / approved attribution
-> public provenance hygiene
-> real publication evidence when a release is executed
-> fresh-environment acceptance when a release is executed
```

No node may be credited with proof power belonging to a later node.

### WP23-L01 — NO GLOBAL RELEASE-READINESS OWNER

WP-23 SHALL NOT create a universal release registry, scalar readiness epoch, compatibility registry, currentness owner or legal-status database merely to compose the existing owners.

## 2. Release identity and package identity

### WP23-L02 — SEMANTIC RELEASE IDENTITY IS SOURCE-DECLARED

`GAME/ENGINE_VERSION.yaml` is the shipped semantic engine/release contract. Shared DEV/GAME release fields must remain synchronized under current builder/audit contracts, while DEV-only revision metadata must not leak into the shipped engine manifest.

### WP23-L03 — BUILT-PACKAGE PROVENANCE IS DISTINCT

Generated root `RUNTIME_PACKAGE.yaml` identifies the source/provenance of one built runtime package. It is generated by the builder and is not a second semantic-version owner.

### WP23-L04 — FINAL ARCHIVE DIGEST IS DISTINCT

The complete runtime ZIP SHA-256 identifies exact final archive bytes. It is not self-embedded in the archive and is not replaceable by semantic version, package ID, tag name or source commit ancestry.

### WP23-L05 — IDENTITY AXES MAY NOT COLLAPSE

The following implications are invalid:

```text
same semantic version -> same artifact
same package_id -> same artifact
same source commit -> same artifact
same/different tag resolution -> compatibility proof
Git ancestry -> exact artifact identity
```

Exact digest equality proves exact artifact identity. Different released bytes require affirmative compatibility support from the exact candidate under current update/migration owners.

## 3. Package construction and install boundary

### WP23-L06 — GAME IS THE SHIPPED SOURCE BOUNDARY

All valid current files under `GAME/` are release-facing runtime source. `DEV/` is development-only and shall not be injected into the runtime package.

### WP23-L07 — OPEN-WORLD GAME PASSTHROUGH

The builder should continue to package valid `GAME/` content recursively without a hand-maintained ordinary-file include list, plus the one generated package-provenance entry.

A future valid `GAME/` file therefore automatically becomes a package/install/legal/public-provenance consumer.

### WP23-L08 — FLAT PACKAGE SHAPE

Installable runtime packages must expose required runtime markers/directories at archive root and must not expose repository wrappers such as `GAME/` or `DEV/`.

### WP23-L09 — SOURCE ARCHIVE IS NOT RUNTIME PACKAGE

Repository-generated source snapshots must not be accepted as installable runtime assets merely because they contain `GAME/` somewhere inside the source tree.

### WP23-L10 — EXACT RUNTIME ROOT

Once a runtime package is selected, package-relative reads must remain bound to that exact validated runtime root. Runtime files from different package identities must not be merged or borrowed across sibling roots.

### WP23-L11 — REPRODUCIBILITY IS A SOURCE-BUILD INVARIANT

Deterministic/reproducible source builds, package-shape validation, generated provenance and packaged generator smoke are current source/build evidence. They are necessary but not sufficient proof of a production publication.

## 4. Version / update / migration composition

### WP23-L12 — VERSION NAMESPACES REMAIN OWNER-LOCAL

Engine release, engine-bound component revision, contract/schema version, campaign/storage generation, catalog generation, ruleset package/compatibility generation and artifact digest retain their accepted independent semantics.

Numbers across namespaces are not comparable compatibility evidence.

### WP23-L13 — RELEASED-V1.0+ COMPATIBILITY IS CONSUMED FROM WP-20

WP-23 does not redefine WP-20 compatibility/migration law. It requires a release artifact to carry/route whatever exact immutable support current WP-20 law requires when released-v1.0+ evolution makes that support applicable.

### WP23-L14 — ABSENCE OF DORMANT FUTURE REALIZATION IS NOT A PRERELEASE DEFECT

Future migration-edge/transform machine realization that has no current released-v1.0+ source/target obligation remains deferred until its owner trigger occurs.

### WP23-L15 — REOPEN THRESHOLD

WP-20 may be reopened only by a demonstrated contradiction, unsatisfied current release consumer or insufficiency of the accepted owner. Thematic overlap is not enough.

### WP23-L16 — UNSUPPORTED / INDETERMINATE FAIL CLOSED

Release/update handling must preserve current fail-closed outcomes for unsupported or indeterminate compatibility. Version order, tag order, schema/generation adjacency or Git ancestry must not manufacture compatibility or migration support.

## 5. Public legal / provenance boundary

### WP23-L17 — PUBLIC-TREE SCOPE

The public-provenance boundary applies to the current public contents of `DEV/` and `GAME/`, regardless of whether an artifact is current-owner prose, research, design history, old proposal, test, audit, runtime documentation or other retained current-tree material.

Git history is not rewritten.

### WP23-L18 — PROHIBITED SOURCE-SPECIFIC DEVELOPMENT/RESEARCH PROVENANCE

Current public `DEV/` and `GAME/` must not retain narrative whose purpose is to record which external sites, authors, projects, products, articles, studies or analogous outside sources were consulted, compared, adopted, rejected or used as development inspiration/evidence.

Public HDM semantics must be stated independently in HDM terms.

### WP23-L19 — REQUIRED LEGAL / APPROVED ATTRIBUTION IS PRESERVED

Mandatory license/legal attribution and separately explicit Product-Owner-approved attribution are outside the prohibition and must remain where required by their owners and release payload.

### WP23-L20 — HDM TECHNICAL ARTIFACT PROVENANCE IS PRESERVED

Technical provenance needed to identify or validate HDM artifacts remains permitted/required, including applicable:

- exact source/commit SHA;
- release/tag identity;
- generated package provenance;
- final hashes/digests;
- version/generation identity;
- migration/update lineage;
- deterministic publication/currentness evidence.

### WP23-L21 — CURRENT OPERATIONAL FACTS ARE NOT AUTOMATICALLY PROHIBITED

An external name/reference may remain when it is a current operational/product/legal fact rather than a development-source trail, for example actual supported host/product boundaries, repository/release transport, official runtime rules-source routing or licensor/material identification required by attribution.

No global external-name/URL blacklist is architecture authority.

### WP23-L22 — INTERNAL / SOURCE-NEUTRAL HDM EVIDENCE MAY REMAIN

Internal experiments, project-owner reconciliation, machine inventories and independently rewritten/source-neutral HDM research may remain when they do not preserve prohibited source-specific development history.

A path such as `research/` is neither automatic permission nor automatic prohibition.

## 6. Sanitation / retirement law

### WP23-L23 — PRESERVE HDM CONCLUSIONS BEFORE REMOVING SOURCE HISTORY

If a current public artifact mixes useful HDM semantics, exclusions, negative requirements, defer/revisit triggers or technical evidence with prohibited development-source narrative, the HDM content must first remain available in an appropriate current artifact before the source-specific trail is removed.

### WP23-L24 — FULL CURRENT-TREE RETIREMENT IS ALLOWED WHEN SEMANTICS ARE ALREADY OWNED

A source-history research artifact may be removed from the current public tree when current accepted owners already retain all material HDM decisions/constraints and no unique current defer/revisit obligation or technical evidence depends on the file.

Removal is current-tree retirement only; history remains available through repository history.

### WP23-L25 — MIXED ARTIFACTS ARE SANITIZED, NOT BLINDLY DELETED

Mixed runtime/architecture/topology/transport artifacts must be rewritten or narrowed so that source-specific development narrative disappears while independent HDM conclusions remain.

### WP23-L26 — HISTORICAL IMPLEMENTATION PREFERENCES DO NOT BECOME REQUIREMENTS

A noncanonical/historical external implementation preference does not constrain future implementation. Component/tool/library selection must be justified from current HDM requirements and later authorized implementation planning.

### WP23-L27 — ROUTING MUST RECONCILE WITH RETIREMENT

When a current-tree source-history artifact is removed or materially narrowed, current routing/index/check/test references that relied on that artifact must be repaired or reclassified in the same coherent realization.

---

## 7. Verification architecture

### WP23-L28 — SOURCE CI PROVES ONLY ITS ACTUAL CHECKS

A green source workflow on exact HEAD proves only the maintenance audit and tests actually executed by that workflow. It does not prove a GitHub Release exists, an asset was uploaded correctly, or a fresh consumer environment accepts it.

### WP23-L29 — BUILD INTEGRATION PROOF IS BOUNDED

The current release-integration route may prove source build reproducibility, flat package shape, generated package provenance and packaged generator smoke. It must not be credited as production publication or fresh-Project acceptance.

### WP23-L30 — PUBLIC-PROVENANCE MACHINE CHECKS ARE BOUNDED REGRESSION EVIDENCE

Machine checks prevent known prohibited current-tree source-history regressions and stale machine requirements for such provenance. They do not claim semantic classification through a naive global external-name/URL blacklist.

A future new ambiguous public artifact still requires owner-aware classification.

### WP23-L31 — RELEASE-TIME PUBLICATION EVIDENCE

A real release readiness claim for one exact release must bind at least to the actual tag/source basis, actual release workflow outcome, actual uploaded runtime asset and exact checksum/identity evidence required by current release owners.

### WP23-L32 — FRESH-ENVIRONMENT ACCEPTANCE IS RELEASE-TIME / POST-REALIZATION PROOF

Where the release checklist requires testing an actually published runtime asset in a fresh supported host/project environment, that evidence cannot be manufactured during architecture work by a source-tree surrogate.

## 9. Explicit negative requirements

The release architecture must not:

1. package `DEV/` into the runtime;
2. accept source snapshots as installable runtime assets;
3. merge sibling runtime roots;
4. equate semantic version with exact artifact bytes;
5. infer compatibility/migration from ordering/ancestry alone;
6. treat green source CI as production publication proof;
7. treat legal-file parity as complete public-provenance hygiene;
8. remove mandatory/approved attribution during provenance sanitation;
9. remove required technical artifact provenance;
10. use a global external-name/URL blacklist as provenance authority;
11. retain source-specific development history merely because a file is historical/research/design material;
12. silently discard HDM-native semantics/revisit triggers while sanitizing mixed artifacts;
13. invent a new release/compatibility/currentness registry;
14. execute release/tag/deployment during WP-23 architecture work;
15. reopen WP-20 without its actual reopen threshold.

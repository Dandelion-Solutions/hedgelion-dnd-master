# 6. Step 5 — Candidate implementation-planning-readiness specification

## 6.1 Purpose

This is not an implementation plan and must remain under `design/`, not `specs/`. Canonicalization happens only at Step 8 after independent Step-6 criticism and Step-7 resolution.

## 6.2 Required candidate structure

The candidate must be sufficiently concrete that the Step-6 reviewer can attack it without reconstructing hidden chat reasoning.

At minimum include:

### A. Authority and scope

- what WP-27 readiness owns;
- what remains owned by prior semantic/runtime/persistence/release contracts;
- explicit non-goals and rejected global abstractions.

### B. Candidate readiness/workstream graph

Derive candidate workstreams from the 145 readiness records.

Aggregation is allowed and encouraged where it simplifies planning, but every aggregate must preserve an inspectable reverse mapping:

```text
source/readiness ID(s)
-> candidate workstream ID
-> current owner(s)
-> destination family
-> activation state
-> dependencies
-> proof obligations
-> Version Impact / migration route
```

No readiness record may disappear merely because several records share a theme.

### C. No-work terminal preservation

Account for all 79 no-work terminals by class and preserve their negative/dormant/already-realized meaning. They must not silently become candidate workstreams.

### D. Dependency DAG

Describe prerequisite relations without forcing unrelated owner-local streams into one global sequence.

Preserve, where applicable:

```text
semantic/persistent shape
-> generator/template/loader/validator realization
-> runtime producer/consumer realization
-> compatibility/migration machinery when actually triggered
-> deterministic proof
-> scenario / empirical proof
-> release-time gates
```

### E. Version / compatibility / migration routing

For every candidate workstream or coherent family, retain the later Version Impact Gate class and migration/update consequence without predeclaring bumps or migrations that depend on an implementation choice not yet made.

### F. Verification channel separation

Keep distinct:

- current realized deterministic verification;
- future deterministic TDD/contract verification;
- scenario acceptance;
- real-target empirical / Protocol-4 work;
- release-time acceptance.

### G. PO and Round-2 continuity

Provide compact but mechanically inspectable mapping showing that:

- PO-001..PO-010 remain represented;
- all 82 DIAMOND/STRONG dispositions remain represented through their current Step-2 routes;
- S14/S53/D15 and any other later-refined items retain their current meaning.

Do not copy all 82 records if a mechanically lossless mapping to Step-2 IDs is sufficient.

### H. Machine reverse-conformance implications

Preserve the Step-2 `R27-M*` / `R27-X*` conclusions that affect planning, including already-realized support, extension points, stale debt and verification-only/historical surfaces. Current machine presence must not become semantic authority.

### I. High-risk probes

Carry forward explicit candidate consequences for `R27-P01..R27-P08`. A Step-2 PASS does not permit Step 5 to drop the constraint the probe was protecting.

### J. Implementation-selectable detail

Explicitly list important choices intentionally delegated to implementation planning so the Step-6 critic can distinguish legitimate flexibility from an architecture gap.

### K. Blocker/reopen result


# Runtime package provenance amendment

Date: 2026-08-18
Status: approved-design self-review amendment, implementation not started
Amends: `2026-08-18-multi-runtime-cache-and-maintenance-continuity-design.md`

## 1. Why this amendment is required

The campaign MANIFEST can store the source commit of the runtime it last accepted, but a candidate ZIP must also carry trustworthy provenance for the bytes it contains.

Resolving the current Git tag is not enough. Example:

1. campaign accepted an older `v0.8` package built from commit A;
2. `v0.8` is later moved/recreated at descendant commit B;
3. an old local ZIP built from A still exists;
4. asking GitHub what `v0.8` points to now returns B, which does not prove that the old ZIP contains B.

Therefore same-version forward/downgrade classification cannot safely use only the filename/tag plus current GitHub ref state.

## 2. Generated artifact manifest

Every newly built runtime ZIP MUST contain a builder-generated top-level file:

```text
RUNTIME_PACKAGE.yaml
```

This file is package/artifact provenance. It is not campaign canon and it is not a replacement for `ENGINE_VERSION.yaml`.

Responsibilities are split deliberately:

- `ENGINE_VERSION.yaml` — source-declared semantic/runtime contract: engine version, release status, repository, owner, rules/schema baseline, compatibility, recommended tag;
- `RUNTIME_PACKAGE.yaml` — provenance of this exact built artifact: logical package identity and source state from which these bytes were produced;
- campaign `MANIFEST.engine.current.package_sha256` — digest of the complete ZIP bytes actually accepted by that campaign.

`package_sha256` MUST NOT be embedded inside `RUNTIME_PACKAGE.yaml`, because a file cannot contain the cryptographic hash of the final archive that contains that same file without introducing a circular definition. The digest is computed after ZIP finalization.

## 3. `RUNTIME_PACKAGE.yaml` fields

Canonical shape:

```yaml
schema_version: 1
engine_version: "0.8"
package_id: "v0.8"
source_state: tagged
source_ref: "v0.8"
source_commit_sha: "<exact commit sha>"
```

Allowed `source_state` values for the initial implementation:

- `tagged` — package is built from the exact tagged checkout/ref; `source_ref` is that tag and `source_commit_sha` is the commit it resolves to;
- `clean_head` — non-tag development/pre-tag package built from a clean Git worktree; `source_ref` may be `HEAD` and `source_commit_sha` is exact HEAD;
- `dirty_worktree` — local development package includes uncommitted bytes; `source_commit_sha` MUST be null as exact artifact provenance cannot truthfully be represented by HEAD alone;
- `non_git` — exceptional non-Git development build; source commit/ref are null.

For a normal published release package:

```yaml
source_state: tagged
package_id: "v<engine_version>"
source_commit_sha: "<tagged commit>"
```

For an authorized development package, logical identity remains development identity, for example:

```yaml
package_id: "dev-v0.8"
```

A clean development build may retain its exact HEAD source SHA. A dirty development build relies on package SHA-256 as exact artifact identity and cannot participate in automatic ancestry classification.

## 4. Builder ownership and no worktree file

`RUNTIME_PACKAGE.yaml` is generated by the release builder. Developers do not manually maintain it under `GAME/`.

The builder MUST construct the YAML payload in memory and write it directly as a ZIP entry. It MUST NOT create, stage, or leave a physical `RUNTIME_PACKAGE.yaml` in the repository worktree, `GAME/`, `builds/`, or another staging directory merely to package it.

Therefore `RUNTIME_PACKAGE.yaml` does NOT belong in `.gitignore`: under the supported build path there is no generated worktree file to ignore.

This creates one deliberate exception to the simple payload rule:

> Runtime ZIP composition is all valid files recursively under `GAME/`, flattened to archive root, plus exactly one builder-generated in-memory top-level `RUNTIME_PACKAGE.yaml` provenance entry.

The builder MUST NOT maintain a hand-written include list for GAME contents.

No other DEV file is injected into the package.

The runtime package validator MUST require both:

```text
ENGINE_VERSION.yaml
RUNTIME_PACKAGE.yaml
```

directly at the package root for packages created under the new contract.

This implementation cycle intentionally does not support legacy runtime ZIPs that predate `RUNTIME_PACKAGE.yaml`.

## 5. Package discovery without eager extraction

Bootstrap may open supported ZIPs and read their root metadata directly without extracting the full archive.

Cheap package indexing reads only what is required to classify candidates, including:

- archive filename;
- `ENGINE_VERSION.yaml`;
- `RUNTIME_PACKAGE.yaml`;
- computed ZIP SHA-256 when needed for exact matching/cache identity.

Full extraction remains lazy and happens only after exact campaign/new-game package resolution.

## 6. Candidate provenance rules

For a candidate ZIP, ancestry classification MUST use `RUNTIME_PACKAGE.source_commit_sha`, not a SHA inferred only by resolving its package_id/tag name at the current moment.

Given campaign current commit A and candidate package commit B:

- exact package digest match -> known exact artifact;
- A == B with different package digest -> same source commit but different bytes; do not silently accept;
- A ancestor of B -> forward same-version refresh candidate;
- B ancestor of A -> downgrade candidate;
- diverged -> ambiguous replacement;
- candidate source SHA null -> ancestry unavailable; explicit authorized acceptance required unless digest already matches.

A single bounded server-side compare/ancestry operation is sufficient for A versus B. No commit-history enumeration is required.

Candidate preference and silent same-version refresh behavior are further refined by `2026-08-18-runtime-selection-and-storage-baseline-amendment.md`.

## 7. Campaign MANIFEST relationship

The new campaign MANIFEST engine fields remain as specified in the parent design:

```yaml
engine:
  created_with:
    version: "0.8"
    package_id: "v0.8"
    source_commit_sha: "<sha|null>"

  current:
    version: "0.8"
    package_id: "v0.8"
    source_commit_sha: "<sha|null>"
    package_sha256: "<sha256>"
    adopted_at: "<timestamp>"

  update_policy: ask
```

On campaign creation or successful refresh/update, these portable fields are copied/derived from the validated package metadata plus the computed final ZIP digest.

`current_runtime_root` remains ephemeral and is never written into MANIFEST.

## 8. Additional validation requirements

Implementation must test that:

1. builder injects exactly one root `RUNTIME_PACKAGE.yaml` without a `GAME/` wrapper;
2. the provenance payload is generated in memory and no worktree/staging `RUNTIME_PACKAGE.yaml` is created;
3. all normal GAME files still pass through automatically without an include list;
4. published/tag package records the exact tagged commit represented by the ZIP;
5. clean-head development package may record exact HEAD;
6. dirty-worktree package does not falsely claim HEAD as exact artifact provenance;
7. bootstrap indexes package provenance without full extraction;
8. moving a tag later cannot make an old ZIP falsely appear to contain the new tagged commit;
9. package SHA remains an external digest of final ZIP bytes and is never self-embedded.

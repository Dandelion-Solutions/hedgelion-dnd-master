# Persistence Transport and Transaction Discipline

framework_module_version: 0.2.0
load_when: a campaign/live/storage publication boundary has already been decided, explicit save transport, checkpoint publication, campaign migration
precedence: authoritative for HOW GitHub writes are sequenced; it does not create ordinary gameplay save boundaries

## Boundary ownership

Do not decide save timing here. `DURABILITY_GUARD.md` owns ordinary gameplay WHEN; `SAVE_CONTRACT.md` owns explicit save; multiplayer/live/access modules may explicitly force shared boundaries. If none of those authorities says publish now, this module does nothing.

## Transport profiles

### CAMPAIGN_TREE_TXN — durable `campaign/*`
All ordinary campaign writes use:

`create_tree(base pinned tree, dirty delta) -> ref check -> create_commit(parent pinned HEAD) -> update_ref(force=false)`

Use this even for one dirty campaign file. Do not mix `create_file`, `update_file`, or `delete_file` into ordinary campaign state publication.

### LIVE_STATE_CAS — active `live/*`
`LIVE_SCENE.md` owns its one-file `LIVE_STATE.yaml` CAS protocol. Do not mix it with campaign-tree writes on the same live ref.

### STORAGE_METADATA_SINGLE — storage default branch
Rare root storage metadata maintenance may use Contents API. It is a separate transaction from campaign publication.

## Transaction snapshot

At transaction start freeze repository, target ref, authorization, `pinned_head_sha`, known/base tree SHA, complete semantic dirty path set, final contents/deletions, and persistence reason.

Discover the full logical delta before mutation. Causally related changes publish together. No operation may advance a campaign ref except the final `update_ref`.

## Known frontier

Maintain `known_head_sha`, `known_tree_sha` when available, loaded canonical records, and dirty working records.

After successful own publication, created commit/tree become the known frontier immediately. Do not refetch HEAD/files merely to confirm your own successful write.

## Base-tree path preservation barrier

For an EXISTING campaign, every normal CAMPAIGN_TREE_TXN MUST build from the pinned HEAD tree. The only normal from-scratch campaign tree is the initial blank scaffold generated by `NEW_CAMPAIGN_FAST_PATH.md`.

For existing campaigns:
- set `base_tree_sha` to the tree of `pinned_head_sha`;
- include only semantically dirty paths plus explicit deletions;
- inherit every other blob exactly from the base tree;
- never reconstruct the whole campaign tree from parsed local copies;
- never parse/reserialize an unchanged YAML/JSON/Markdown file merely for convenience;
- quote/whitespace/key-order/array-style drift is not semantic dirtiness.

README is dirty only for the mutable overview allowed by `CAMPAIGN_IDENTITY.md`; preserve all protected/outside-marker bytes exactly. `RULES/HOUSE_RULES.md`, templates/helpers and unrelated indexes/entities remain untouched unless independently dirty.

Before commit creation assert that every changed path has a semantic dirty reason. Unexpected unrelated changes invalidate the plan.

## Publication algorithm

Given pinned HEAD `H`:
1. lazily obtain H's tree SHA if not already cached;
2. create one tree from that base tree containing the complete dirty delta;
3. probe the target ref once after tree preparation and immediately before commit creation;
4. if current HEAD != H, abort before `create_commit`, repin/target-refresh affected dependencies, re-evaluate and rebuild;
5. assert intended parent == H;
6. create one commit;
7. immediately `update_ref(force=false)`;
8. on success adopt commit/tree as known frontier and clear the published dirty set.

If the ref moves in the tiny window after commit creation, non-force update must fail; invalidate the transaction, repin and rebuild. Never force the prepared commit. An unreachable commit object is acceptable as an exceptional race artifact.

## Error invalidation

Any conflict implying stale state (non-fast-forward, stale blob/SHA mismatch, ref moved) invalidates the affected transaction snapshot. Do not keep publishing pieces from mixed versions. Repin and reread only touched/dependent records.

A self-induced race caused by mixing APIs/overlapping transactions is a runtime bug; recover by rebuilding, never by force-pushing.

## Checkpoints

Publication does not imply checkpoint creation. Create/update a checkpoint only when session/recovery policy independently says exact recovery benefits from one (session end/pause, major transition, complex mid-procedure stop, risky migration/repair, etc.).

## Performance targets

Most singleplayer live turns: zero GitHub calls because no boundary fires.
First persistence with unknown tree: normally 5 calls (fetch commit tree + create_tree + ref probe + create_commit + update_ref).
Later persistence with cached tree: normally 4 calls.
Successful own publication: zero immediate confirmation reads.

## Player-facing silence

Routine successful persistence is infrastructure. Surface it only when the user explicitly asks, publication fails/conflicts, canon/adjudication may change, or user/owner action is required.

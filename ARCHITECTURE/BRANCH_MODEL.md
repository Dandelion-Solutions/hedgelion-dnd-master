# Модель веток и кампаний

## Цель

`main` содержит только общую систему AI Dungeon Master: Framework, схемы данных, шаблоны, bootstrap и документацию. Конкретные миры, персонажи и результаты игр никогда не должны попадать обратно в `main`.

После подготовки стабильной версии движка соответствующий commit помечается release-тегом вида `engine-v1.0.0`. Новая кампания создаётся отдельной долгоживущей веткой от конкретного engine release.

Рекомендуемое имя:

`campaign/<короткое-имя>`

Например:

`campaign/denis-01`
`campaign/shared-world-01`

## Разделение данных

В `main` находятся:

- `CORE/` — общий Dungeon Master Framework;
- `SCHEMA/` — форматы сущностей и состояния;
- `TEMPLATE/` — шаблоны новой кампании;
- `MIGRATIONS/` — переходы между несовместимыми версиями схем/Framework;
- `INSTALL/` — пользовательская документация;
- `00_DND_BOOTSTRAP.md` — runtime bootstrap.

В campaign-ветке дополнительно появляется каталог `CAMPAIGN/`:

- `CAMPAIGN/MANIFEST.yaml` — идентичность кампании, режим и версия движка;
- `CAMPAIGN/STATE/` — актуальное горячее состояние;
- `CAMPAIGN/INDEX/` — компактные индексы;
- `CAMPAIGN/WORLD/` — постоянные сущности мира;
- `CAMPAIGN/LOG/` — append-only журнал событий;
- `CAMPAIGN/CHECKPOINTS/` — контрольные состояния.

`CAMPAIGN/` не должен существовать в наполненном игровыми данными виде в `main`.

## Обновление общего Framework

`main` может развиваться после начала кампании.

По умолчанию обновления из `main` интегрируются в campaign-ветку через merge. Это сохраняет SHA уже существующей истории кампании и безопаснее для параллельных игровых чатов.

Rebase допускается только как явная maintenance-операция для остановленной ветки, когда гарантированно нет других активных сессий/писателей. После rebase все ранее закешированные SHA считаются недействительными и требуется полный resync runtime-состояния.

Если обновление меняет структуру persistent data, одного merge недостаточно. Для такой версии Framework должна существовать миграция в `MIGRATIONS/`, а `CAMPAIGN/MANIFEST.yaml` должен фиксировать применённую версию схемы.

## Однопользовательский режим

`mode: singleplayer`

Предполагается один писатель — AI Dungeon Master. Внутри одной игровой сессии разрешено использовать закешированный HEAD и SHA уже прочитанных записей, чтобы не делать лишние запросы.

При старте нового чата выполняется синхронизация с HEAD campaign-ветки.

По явной команде пользователя `resync`, `перечитай ветку`, `обновись с GitHub` или эквивалентной агент обязан перечитать HEAD и обновить рабочий набор до продолжения игры.

Любая не-fast-forward ошибка при сохранении означает, что ветка изменилась извне. В этом случае агент не должен перетирать изменения: требуется resync, повторное разрешение конфликтующих данных и только затем новая попытка записи.

## Многопользовательский shared-world режим

`mode: multiplayer`

Режим включается и выключается только явно. Самостоятельно переключать режим агент не имеет права.

В multiplayer несколько чатов/игроков могут менять один мир. Поэтому перед каждым ходом, способным изменить persistent state, агент:

1. получает текущий HEAD campaign-ветки;
2. сравнивает его с HEAD, на котором построен локальный working set;
3. если SHA изменился — определяет изменения между SHA и перечитывает затронутые state/entity/index records;
4. только после синхронизации разрешает действие игрока;
5. сохраняет весь результат хода одним атомарным Git commit;
6. двигает branch ref только fast-forward;
7. при конфликте HEAD отказывается от слепой записи, синхронизируется и повторно оценивает последствия действия с учётом нового мира.

Это optimistic concurrency. Первый успешно записавший ход становится частью канона; другой ход должен учитывать уже произошедшее изменение мира.

## Транзакция игрового хода

Один логически завершённый state-changing ход должен по возможности соответствовать одному Git commit.

Commit включает одновременно:

- новую append-only запись события;
- изменения `STATE`;
- изменения затронутых сущностей `WORLD`;
- изменения соответствующих `INDEX`;
- при необходимости обновление checkpoint metadata.

Для атомарности следует использовать Git tree/commit/ref операции, а не последовательность независимых Contents API commits.

Если действие игрока не изменило долговременное состояние, отдельный commit не требуется.

## Git history и Event Log

Git history — технический аудит хранилища.

`CAMPAIGN/LOG` — семантическая история игрового мира.

Они дополняют друг друга. Git commit не заменяет Event Log, потому что игровой журнал должен содержать причинные и временные связи мира, а не только diff файлов.

## Несколько кампаний

Каждая кампания имеет отдельную ветку и собственный `CAMPAIGN/MANIFEST.yaml`. Кампании никогда не мержатся друг в друга и никогда не мержатся обратно в `main`.

Один репозиторий поэтому может безопасно хранить любое число независимых кампаний, созданных от разных версий Framework.
